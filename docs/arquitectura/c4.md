# Modelo C4 — Canal Chatbot

Todo lo que aparece aquí proviene de [`modularizacion.md`](modularizacion.md), del [ADR-0025](adr/ADR-0025-monolito-modular-por-capacidad.md), de los `design.md` de [`openspec/specs/`](../../openspec/specs/), de [`contratos-integracion.md`](../contratos-integracion.md) y de [`modelo-datos.md`](../modelo-datos.md). Si un diagrama contradice a una spec, manda la spec y este documento se corrige.

**Cómo leer los diagramas**

- Están escritos con la sintaxis C4 de Mermaid (`C4Context`, `C4Container`, `C4Component`), que GitHub renderiza directamente. Esa sintaxis es experimental: el acomodo automático reparte los elementos en filas según el ancho de la pantalla, por lo que en una pantalla angosta algunas flechas pueden cruzar cajas. Las tablas bajo cada diagrama son la referencia exacta.
- Se omite a propósito el **nivel 4 (código)**: la estructura de clases vive en los repositorios `G3-Chatbot-backend` y `G3-Chatbot-frontend`, y la documentarían mejor sus propias herramientas.

Quién usa el Canal Chatbot y de qué sistemas depende. El canal no es dueño del catálogo, del stock, de los usuarios, de los pedidos ni de los despachos: los consulta por API ([ADR-0013](adr/ADR-0013-solo-referencias-locales-a-agregados-externos.md)).

Notas:

- **Ventas no recibe las imágenes del chat.** La evidencia de devolución (SPEC-21) se sube a Ventas desde su formulario; las imágenes adjuntas al chat viven solo en el bucket propio del canal.
- **El pago y el SMS no son sistemas externos.** El pago se procesa con un simulador propio detrás de `PaymentGateway` ([ADR-0014](adr/ADR-0014-pago-simulado-detras-de-paymentgateway.md)). El OTP del celular está diseñado para salir por un `SimulatedSmsSender` propio ([ADR-0015](adr/ADR-0015-verificacion-propia-del-celular-por-otp.md)), pero **aún no está implementado**: solo existen la tabla `local_phone_verification` y su adaptador.
- **Marketplace y Retail** son canales hermanos que consumen los mismos módulos; el chatbot no se integra con ellos. La verificación local del celular no se comparte con esos canales (SPEC-04 · *Fuera de alcance*).
- El Gestor de Ventas y el Gestor Comercial de Productos deciden sobre datos que el chatbot muestra (respuestas a reclamos, resoluciones, promociones), pero no usan el canal ([`alcance.md` §2](../producto/alcance.md#2-usuarios-y-roles)).
- Los usuarios con token sin rol `CLIENTE` no pueden comprar: se les cierra la sesión (SPEC-03 · Req. 1).

## Nivel 2 — Contenedores

Las unidades ejecutables siguen siendo un frontend Next.js, un backend FastAPI, un worker y PostgreSQL. Lo que cambia respecto de la vista anterior es que **la unidad interna de trabajo es el módulo**: los 8 módulos viven dentro del mismo backend y del mismo frontend, con ids idénticos, y `shared/` es el kernel. Los cuatro módulos del Marketplace se agrupan en una sola caja; el detalle por módulo está en el nivel 1 y en [`modularizacion.md`](modularizacion.md).

**Protocolos**

| Origen → destino | Protocolo | Uso |
|---|---|---|
| Frontend → Backend API | HTTPS REST/JSON, `Authorization: Bearer <accessToken>`; errores `application/problem+json` con `code` | Crear, listar y buscar conversaciones, enviar mensajes (la respuesta del asistente llega en el stream de la misma respuesta) y ejecutar acciones con efecto |
| Backend API → Frontend | SSE (`Content-Type: text/event-stream`) en la respuesta `200` de `POST /api/v1/chat/conversaciones/{id}/mensajes` | Eventos `aceptado`, `token`, `bloque`, `degradado`, `fin` y `error`. Los errores de validación y pertenencia se responden antes del stream como `application/problem+json`. Si el stream termina sin `fin` ni `error`, el frontend reconsulta una sola vez `GET /chat/conversaciones/{id}/mensajes` (sin `desde`); si no aparece la respuesta, ofrece "Reintentar" |
| Backend API / Worker → módulos | HTTPS REST/JSON con httpx | Token del cliente reenviado cuando el recurso es del titular; token de servicio `modulo-chatbot` para operaciones a nombre del sistema ([ADR-0009](adr/ADR-0009-token-de-servicio-con-servicetokenprovider.md)) |
| Backend API → Proveedor LLM | HTTPS (API del proveedor) | Tool calling con streaming; timeout de 15 s. Con SPEC-23, el contexto puede incluir imágenes en base64 |
| Backend API → Supabase Storage | HTTPS (API de Storage) | Guardar y leer imágenes adjuntas, emitir URLs firmadas y eliminar archivos huérfanos |
| Worker → SMTP | SMTP | Correo de confirmación del pedido |

> **Topología del worker decidida.** El worker corre como servicio propio y en una única instancia, nunca dentro del proceso de la API, para que varias réplicas de la API no ejecuten los jobs más de una vez. Decisión provisional del 2026-10-10: [ADR-0020](adr/ADR-0020-despliegue-en-railway-vercel-y-supabase.md); ver la [vista de despliegue](#vista-de-despliegue).

## Nivel 3 — Componentes del backend

El backend es un **monolito modular**: la unidad de frontera es el módulo, y dentro de cada módulo se conserva el corte hexagonal de ADR-0002 (adaptadores inbound → casos de uso → dominio → puertos outbound). Para que la vista sea legible se divide en cuatro vistas:

- **3a — Módulos y dependencias:** los 8 módulos y el DAG que verifica el manifiesto.
- **3b — Interior de un módulo:** el patrón que repite cada módulo (ejemplo con `mod-catalog`).
- **3c — Superficie pública:** qué expone cada `public.py` y qué capacidades sustituyen imports prohibidos.
- **3d — Módulos del frontend:** las rutas y los adapters de cada `mod-*`.

> La agrupación histórica en 8 casos de uso (ADR-0018) queda **reemplazada en la práctica** por los 8 módulos de ADR-0025. Los nombres de servicios y adaptadores salen de los `MODULE.md` y de los `design.md`.

### 3b — Interior de un módulo (patrón común)

Todos los módulos repiten la misma forma. El ejemplo es `mod-catalog`; `mod-cart`, `mod-checkout`,
`mod-orders` y `mod-postventa` cambian los nombres, no la estructura.

```mermaid
C4Component
    title Backend API - Nivel 3b: interior de mod-catalog

    Container_Boundary(mod_catalog, "mod-catalog") {
        Component(router, "catalog_router.py", "Adaptador inbound", "GET /catalogo/productos, /{id}, /promociones, /disponibilidad; tags=[MODULE_ID]")
        Component(uc, "ManageCatalogUseCase", "Caso de uso", "Búsqueda, detalle, promociones, recomendación y disponibilidad")
        Component(domain, "Reglas puras", "Dominio", "ProductNormalizer, VariantResolver, StockValidator, price_projection")
        Component(ports, "ProductCatalogPort / InventoryPort", "Puertos", "Contratos hacia Productos e Inventario")
        Component(adapters, "ProductsClient / InventoryClient", "Adaptadores outbound", "httpx con timeout y URL base parametrizada")
        Component(public, "public.py", "Superficie pública", "provide_catalog_service, provide_product_catalog, Argumentos y reglas reutilizables")
    }

    Container(chat, "mod-chat", "Módulo orquestador", "ToolRegistry y acciones directas")
    System_Ext(pro, "Productos y Ofertas", "API externa")

    Rel(chat, public, "importa solo public.py")
    Rel(public, uc, "expone")
    Rel(router, uc, "invoca")
    Rel(uc, domain, "aplica")
    Rel(uc, ports, "depende de")
    Rel(adapters, ports, "implementa")
    Rel(adapters, pro, "REST/JSON", "HTTPS")
```

| Capa interna | Sí | No |
|---|---|---|
| `adapters/http` | Validar DTOs, aplicar dependencias, llamar a un caso de uso, mapear `code` a HTTP | Lógica de negocio, httpx, SQL |
| `application` | Orquestar puertos, ordenar precondiciones, controlar la transacción | Importar FastAPI, httpx o SQLAlchemy; leer `os.environ` |
| `domain` | Reglas puras y testeables sin I/O | Cualquier import de framework o red |
| `ports` | Interfaces mínimas que el caso necesita | Implementaciones |
| `adapters` (outbound) | Único lugar con httpx/SQL/SMTP/LLM; timeouts propios; normalizar `codigo` → `code` | Decidir reglas de negocio |
| `public.py` | Reexportar lo que otro módulo puede usar | Exponer `domain/`, `application/` o `adapters/` ajenos |
| `module.py` | `MODULE_ID`, `build_router(options)`, `configure(container)` | Lógica de negocio o listas de módulos |

## Preguntas abiertas

> La topología del worker y el despliegue quedaron resueltos, de forma provisional, por el [ADR-0020](adr/ADR-0020-despliegue-en-railway-vercel-y-supabase.md).

1. **Contrato OpenAPI ↔ frontend.** El manifiesto del frontend declara endpoints, pero ningún gate los compara con `docs/openapi.json`. El test manual ya incluye `POST /contacto/celular/verificar-otp`, que el backend no expone. ¿Se implementa el script de contrato o se retira el endpoint del manifiesto mientras SPEC-04 no exista?
2. **SPEC-04 y SPEC-23.** La tabla `local_phone_verification` y el modelo `attachment` existen, pero faltan OTP, `CheckoutGuard`, endpoints de adjuntos y `AttachmentStorage`. ¿Entran en el próximo hito o se retiran del contrato?
3. **`shared/` y el worker.** El worker de outbox vive en `shared/`; si crece con jobs de un módulo concreto, hay que decidir si se mueve al módulo dueño o se queda como kernel.
